# dev-hcitest

## Overview

Three Incus VMs (`hcitest[01-03]`) used to test `hci[01-03]`'s NixOS configs. `hcitest[01-03]` use the same `nix/modules/hci` module as `hci[01-03]` for configuration but have their own set of secrets `secrets/hcitest.enc.yaml`.

Terraform is used to provision the Incus VMs, install NixOS, and deploy the configurations; the latter two steps are done using `nixos-anywhere`.

`hcitest` is primarily for testing NixOS configuration and software/package/service compatibility and functionality. Items such as drivers, firmware, network routing/switching, etc. are not covered and are out of scope.

## How it Works

### Network

```
incus host
│
├── incusbr0                  172.16.0.1/24
│   │                         nat · dhcp
│   │
│   └── eth0 (enp5s0)         oob management
│                             172.16.0.1{N} (static dhcp lease)
│
│
└── hcitest-trunks            no host ip · isolated · mtu 9000
    │
    ├── eth1 (enp6s0)         data trunk
    │   └── vlan 50           172.16.1.1{N}/24
    │
    └── eth2 (enp7s0)         storage trunk
        ├── vlan 40           172.16.2.1{N}/24
        └── vlan 41           172.16.3.1{N}/24
```

Network configuration is the primary discrepancy between `hci[01-03]` and `hcitest[01-03]`. `hcitest` uses the `oob mgmt` NIC for default gateway and DNS; this is done to avoid requiring the incus host to have connectivity to the real vlan 50 or emulating the entirety of the homelab network virtually. Instead, use the default `incusbr0` bridge with NAT.

Traffic between `oob mgmt` and `data/storage trunks` is kept separate like in production by using separate bridges. Incus requires `dns.mode=none` when multiple NICs are on the same network to avoid DNS clashes from Incus's autogenerated DNS entries.

### Devices

| Incus Device  | Guest PCI Path     | Purpose                               |
| ------------- | ------------------ | ------------------------------------- |
| `eth0`        | `pci-0000:05:00.0` | `hci.network.interfaces.oobMgmt`      |
| `eth1`        | `pci-0000:06:00.0` | `hci.network.interfaces.dataTrunk`    |
| `eth2`        | `pci-0000:07:00.0` | `hci.network.interfaces.storageTrunk` |
| `root` (nvme) | `pci-0000:08:00.0` | `hci.disks.systemDisk`                |
| `osd` (nvme)  | `pci-0000:09:00.0` | ceph osd disk (unmanaged by nixos)    |

> [!NOTE]
> **PCI Order:** Though not explicitly documented, Incus pci path / slot assignment is deterministic by fixed rules (see [`devices_sort.go`](https://github.com/lxc/incus/blob/main/internal/server/device/config/devices_sort.go)).
> Slots start at bus 05 and continue in the order of: NICs (ordered by name), root disk, then extra disks.
> Editing devices will shift paths and require updating `nix/hosts/hcitest0{N}` plus regenerating facter (hardware) reports.

### Secrets

`hcitest[01-03]` have their own secrets, separate from `hci[01-03]`. `secrets/hcitest.enc.yaml` has the same entries and structure as `secrets/hci.enc.yaml`.

## Deployment

The Incus VMs are provisioned using `terraform`, and `nixos-anywhere` is used to install and deploy the NixOS configurations. `nixos-anywhere` has terraform modules available for managing deployments: [see here](https://github.com/nix-community/nixos-anywhere/tree/main/terraform). This allows using terraform to manage both the VM infrastructure and the actual deployment + configuration.

Incus VMs are deployed with a `kexec` capable image (e.g. debian cloud), cloud-init is used to provision passwordless ssh access (authentication keys), then `nixos-anywhere` is used to install NixOS and deploy the configuration:

> [!NOTE]
> `scripts/hciadmin-ssh-agent-wrap.sh` is a helper script used to wrap commands with an `ssh-agent`.
> The script loads the `hci-admin` ssh-key from sops (`secrets/hcitest.enc.yaml`).

```bash
cd terraform/incus/dev-hcitest
# admin pubkey: sops --decrypt --extract '["hci_admin_keys"]["ssh"]["pk"]' ../../../secrets/hcitest.enc.yaml
echo "root_ssh_authkeys=[\"ssh-ed25519 AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA hcitest-admin\"]" > ./secrets.auto.tfvars
tofu init
./scripts/hciadmin-ssh-agent-wrap.sh tofu apply

# verify
incus list
./scripts/hciadmin-ssh-agent-wrap.sh ssh root@172.16.0.1{N} nixos-version
```

### Bootstrap Facter (Hardware) Reports

Facter (hardware) reports are part of hosts' NixOS configuration, so they must exist prior to deployment. `nixos-anywhere` can be used to run `nixos-facter` against the unprovisioned VM to generate the report prior to deployment:

1. Provision incus instances without running nixos-anywhere:

```bash
cd terraform/incus/dev-hcitest
./scripts/hciadmin-ssh-agent-wrap.sh tofu apply -target=incus_instance.nodes
```

2. `kexec` each node into the installer and generate facter report:

```bash
# E.g. hcitest01 (172.16.0.11)
NODE=hcitest01
NODE_IP=172.16.0.11
./scripts/hciadmin-ssh-agent-wrap.sh \
    nixos-anywhere --flake "../../../.#${NODE}" --phases kexec \
        --generate-hardware-config nixos-facter "../../../nix/hosts/${NODE}/${NODE}-facter.json" \
        "root@${NODE_IP}"
```

3. `git add` the generated reports (flakes only see files tracked by git)
4. Teardown to start from scratch: `tofu destroy`
